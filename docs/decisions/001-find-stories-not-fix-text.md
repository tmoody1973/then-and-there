# 001 — The centerpiece is finding stories, not fixing text

**Decision.** Then & There's main job is surfacing human stories nobody knows to look for. Repairing bad OCR (the computer-generated text behind each scanned page) is a supporting step, not the headline.

**Why this came up.** The original plan led with "pages nobody can search well," which assumed the OCR was too broken to search. If that was wrong, the demo's big moment would rest on a problem judges could see wasn't real.

**Options.**
1. **Lead with OCR repair.** Strong before/after visuals. But on the pages we tested, the text was mostly readable, so the claim would be overstated.
2. **Lead with discovery** (the system finds the stories for you). Matches what we measured, and matches Tarik's own work finding the story behind the music. Harder to show in one image.
3. **Lead with the games and treat the data as background.** Fun, but weak on the judging's Impact score (30%).

**What we chose and why.** Option 2. Joint: Claude ran the test, Tarik set the direction. One issue of the *Wisconsin Weekly Advocate* (Dec 9, 1898) had only 9–13% non-dictionary words, and the Library's own search found the best story we read (J. E. Ellmore, an Appleton barber) on the first try. It found it only because we already knew the name. Readable but unread.

**What we gave up.** The simplest visual pitch, "garbled text in, clean text out," moves to a supporting role. We kept one real example (The Evening World, Nov 29, 1889: "Nellie Bly's trip" became "Nellie IllyM tri").

**How we'll know if this was right.** Judges and early users can repeat the pitch as "it finds stories" rather than "it fixes OCR," and the discovery count in the submission (section 10 of the design) is large enough to be striking.
